V4.5 Error Handling / Testing / Acceptance

The acceptance bar should prove recommendations are useful, traceable, and unable to mutate rules silently.

Acceptance Model
Traceability

Every suggestion cites facts

Each recommendation links to pattern IDs, drilldown items, runs, work items, tasks, review comments, or evidence.

Safety

No silent edits

Patch previews are inert records until an explicit human apply step exists. Reject/defer never touches files.

Usefulness

Low-noise queue

Repeated issues cluster into stable recommendations; duplicate suggestions are deduped or superseded.

Test Matrix

Contract: recommendation JSON round-trip, statuses, target kinds, evidence refs.

Engine: pattern-to-template mapping, dedupe, confidence, stale/superseded handling.

Patch: generated diff preview is scoped to one target and never writes files.

API: list/detail/action endpoints; team project isolation with x-issuepilot-project.

UI: queue, detail view, accept/reject/defer, empty/error states, keyboard accessible controls.

E2E: quality pattern → recommendation → patch preview → human action history.

Fifth Design Section: Error Handling / Testing / Acceptance

V4.5 fails closed. If evidence is missing, target files are unknown, a patch cannot be generated safely, or the recommendation source becomes stale, the system keeps the recommendation visible with an explicit blocked/stale reason instead of guessing.

Acceptance should prove three things: every recommendation is traceable to evidence, no action silently mutates workflow/skill/project rules, and operator actions are durable and auditable. Team mode must preserve project isolation exactly like V4.4 quality analytics.
